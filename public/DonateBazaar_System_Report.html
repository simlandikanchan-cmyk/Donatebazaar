4.Authentication & Identity

Three independent login channels, all secure by construction.

4.1 Email / Password

  • Standard Laravel auth: RegisteredUserController, AuthenticatedSessionController.
  • Passwords hashed with bcrypt at cost 12 (BCRYPT_ROUNDS=12), via the Hash facade only — no custom/weak hashing.
  • Email verification, password reset, and "confirm password" flows implemented.
  • Session regenerated after login; double-submit guard on the login form.

4.2 Google OAuth

  • GoogleController redirects to Google, handles the callback, and creates/matches the user.
  • Google users get a random bcrypt password (bcrypt(Str::random(32))) — never stored in plaintext.
  • WelcomeGoogleMail welcomes the new user.

4.3 Phone OTP Login

  • OtpController: generates a 6-digit OTP via random_int(100000,999999) (cryptographically secure).
  • OTP stored as Hash::make($otp) with a 5-minute expiry and an attempt counter.
  • Verification uses Hash::check; routes throttled (throttle:5,1 send, throttle:3,1 resend).

4.4 Identity Model Highlights (User.php)

FeatureImplementation
Password protection'password' => 'hashed' cast; hidden from arrays
Fundraiser levelsassignedLevel() via hasOneThrough; max goal + level name
SuspensionisFundraiserSuspended() blocks suspended accounts
KYC statushasApprovedKyc() gates campaign activation
Followed campaignsPolymorphic morphedByMany relationship
Security note: OTPs are never stored in plaintext and expire quickly, and SMS/email channels are rate-limited — mitigating the two most common auth attacks (brute force and replay).

5.Campaign Creation Workflow

The creator experience and the business rules that govern it.

5.1 The 6-Step Wizard

StepFieldsValidation
1. BasicsTitle, goal (₹), category, descriptionRequired; goal ≥ 1
2. DetailsLocation, video URL, dates, featured/urgentend ≥ start
3. UpdatesCampaign updates & documents≥1 update req. (title+body)
4. MediaCover imageJPG/PNG, auto→WebP 1200px
5. ProductsAdmin-suggested or customOptional
6. ReviewSummary + KYC noticeSubmit → KYC

5.2 Fundraiser-Level Gating

FundraiserLevelService::canCreateCampaign() enforces two limits before a campaign can be created:

  • Max concurrent campaigns (max_active_campaigns) — counts active/pending/paused.
  • Max goal amount (max_goal_amount) — hard cap per level.

On update, only the goal cap is re-checked (not the count). Level is resolved from assignedLevel or a default.

5.3 On Submit (CampaignController::store())

  1. Auth check → redirect to login if unauthenticated.
  2. Run fundraiser-level gate; reject with reason if over limit.
  3. Validate all input against CREATE_RULES.
  4. Require ≥1 valid campaign update.
  5. Create Campaign in pending state with unique slug; convert cover to WebP.
  6. Store products (user→pending, admin→approved) and updates.
  7. Clear category cache; send CampaignCreatedMail; redirect to KYC.

5.4 Campaign State Machine

pending→ active→ paused↔ active→ completed
pending→ rejected→ (resubmit) pending

Expiry is handled by a scheduled command and real-time end-date checks. Every transition writes a CampaignLog.

6.KYC & Compliance

Identity verification — a regulated, security-sensitive subsystem.

6.1 KYC Flow (User Side)

  • KycUploadController: user uploads PAN / Aadhaar / Passport to the private disk.
  • Record scoped per campaign_id + owner — a user with multiple campaigns keeps separate KYC records.
  • File stored at kyc-documents/{user}/{campaign}; status set to pending; admins notified.
  • Owner-only access enforced via abort_unless(Auth::id() === ...) on view/serve.

6.2 KYC Review (Admin Side)

  • Admin\KycController: list, approve (verified_by, verified_at), reject (with reason).
  • Secure document serving via response()->file() from the private disk.
  • Campaign approval is hard-blocked until owner KYC is approved.

6.3 Why This Matters (Security)

Sensitive PII (government IDs) is never placed on public storage. The private disk + owner-scoped access + per-campaign isolation means a compromised campaign view cannot leak another user's ID document. This is a deliberate compliance control, not a default.

ID document leakagePrivate disk + owner-only route guards
Cross-campaign data bleedKYC scoped by campaign_id
Fraudulent live campaignsKYC approval required before activation
Stale verificationAdmins can re-request KYC (requestKyc)

7.Payment Pipeline — The Core Engineering

The most complex, highest-risk subsystem. Engineered for correctness under concurrency.

7.1 Three-Step Flow

1. redirectToPayment→ 2. paymentPage (Razorpay order)→ 3. verify (signature check)

7.2 Step 1 — Initiate (redirectToPayment())

  • Rate-limited (10 hits / 60s per user/IP).
  • Validates amount within ₹1–₹500,000.
  • Applies coupon server-side (discount never trusted from client).
  • Checks campaign state (rejects expired/paused/rejected).
  • Stores a 15-minute donation session with cart data.

7.3 Step 2 — Payment Page (paymentPage())

  • Re-validates session (exists, matches campaign, not expired > 900s).
  • Re-validates coupon from DB; falls back to full amount if coupon lapsed.
  • Calculates the 5% platform fee split (platform_fee + net_amount).
  • Creates a Razorpay order (full amount in paise) and a pending Donation row.
  • Saves product donation items; clears session; guards against re-opening a completed payment.

7.4 Platform Fee Model ("Ketto-style")

Razorpay charges the donor the full amount. Internally the system splits it: net_amount = amount − (amount × 5%). The campaign receives net_amount; the platform retains platform_fee. This is recorded on every donation and aggregated at settlement.

8.Payment Integrity & Concurrency

How double-charging, double-crediting, and race conditions are prevented.

8.1 Defense-in-Depth Layers

#ControlMechanismPrevents
1Signature verificationverifyPaymentSignature()Forged "paid" callbacks
2Distributed lockCache::lock('payment_lock_'.$paymentId)Concurrent double processing
3DB row lockDonation::lockForUpdate()Race on the donation row
4Idempotency checkEarly-exit if payment_status==='completed'Retry double-credit
5DB triggertrg_donation_raised_amount_*Double-increment of totals
6Rate limitingRateLimiter on verifyBrute / abuse

8.2 Transaction Pattern

DB::transaction(function () use ($donation, $request) {
    $locked = Donation::lockForUpdate()->findOrFail($donation->id);
    if ($locked->payment_status === 'completed') return;   // idempotent
    $locked->payment_status = 'completed';
    $locked->save();
    Campaign::lockForUpdate()->findOrFail($id)
            ->increment('platform_earnings', $locked->platform_fee);
    $this->decrementProductStock($locked);
    $this->redeemCoupon($locked);
});
// receipt email sent AFTER commit, outside the lock

8.3 Why the DB Trigger Matters

The application does not manually increment raised_amount. A MariaDB trigger recomputes it from the sum of completed donations — the single source of truth. This removes an entire class of bugs (double counting, partial updates, lost writes under load).

8.4 Product Stock & Coupons

  • Stock decremented with a guarded where('remaining_quantity','>=',qty)->decrement().
  • Coupon redemption is atomic, locked, and idempotent (never redeemed twice for the same donation).

9.Webhooks, Refunds & Settlement

Asynchronous money movement, handled safely.

9.1 Webhook Security

  • webhook() verifies X-Razorpay-Signature using hash_hmac('sha256', …) compared with hash_equals() (constant-time — immune to timing attacks).
  • Two-tier guard: missing secret → 500 (alerts us to misconfig); missing signature → 400 (rejected, logged).

9.2 Event Routing

Razorpay EventHandlerEffect
payment.capturedhandlePaymentCapturedMark completed, increment earnings, stock, coupon, email
payment.failedhandlePaymentFailedMark donation failed
refund.processedhandleRefundProcessedCreate Refund, mark refunded, email donor
refund.failedhandleRefundFailedRecord failed refund status

9.3 Refund Integrity

  • Idempotent: skips if a Refund with the same gateway_refund_id exists.
  • Only a completed, not-yet-refunded donation is refundable.
  • All handlers use the same lock + transaction + idempotency pattern as the verify path.

9.4 Settlement (SettlementService)

Batches all completed, pending-settlement donations for a campaign into a CampaignSettlement with gross_amount, platform_fee, and net_amount. This is the payout ledger that reconciles platform earnings vs. what the campaign earns.

12.AI Chatbot (Anthropic Claude)

A streaming, context-aware customer-support assistant.

12.1 How It Works

  • ChatbotController::chat() validates the message (max 1000 chars), then streams from the Claude API (claude-sonnet-4-6) using Server-Sent Events (SSE).
  • Responses are streamed token-by-token to the browser with ob_flush()/flush().
  • Conversation history (last 10 messages) is kept in the session for context.
  • A scoped systemPrompt() restricts the assistant to donation/campaign/payment/refund topics.
Http::withHeaders([ 'x-api-key' => config('services.anthropic.key'),
       'anthropic-version' => '2023-06-01' ])
    ->withOptions(['stream' => true])
    ->post('https://api.anthropic.com/v1/messages', [
        'model' => 'claude-sonnet-4-6',
        'max_tokens' => 500,
        'system' => $this->systemPrompt(),
        'messages' => $history,
        'stream' => true,
    ]);

16.Scalability — Built-In Strengths

Where the architecture is ready for growth.

16.1 Stateless Money Logic

  • All critical money movement relies on DB triggers + locks, so multiple app servers behind a load balancer won't corrupt totals.
  • No in-process state holds financial truth — safe for horizontal scaling.

16.2 Cache & Locks

  • Cache::lock works across servers when the cache driver is shared (Redis/Memcached).
  • Public campaign categories cached (active_campaign_categories, 1-hour TTL).

16.3 Database Performance

  • Dedicated index migrations: add_indexes_to_tables, add_critical_indexes, add_indexes_for_performance.
  • UUIDs generated, foreign keys enforced, polymorphic relations used appropriately.

16.4 Queue-Ready

  • TestQueueJob + jobs table migration present.
  • Receipt/status emails are sent outside DB transactions — decoupled from the request lifecycle.

16.5 Read Path & API

  • Slug-based SEO URLs, sitemap generation, public caching.
  • REST API scaffolded (routes/api: campaigns, donations, events, notifications, payments).

Maturity estimate: ~85% scale-ready for a moderate-traffic production launch.
