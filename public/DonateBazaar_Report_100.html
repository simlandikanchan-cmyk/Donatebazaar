4.System Architecture

How the layers fit together.

4.1 Layered Architecture

HTTP Routes (web / admin / api)→ Middleware (auth, admin, account, author)→ Controllers→ Services (business rules)→ Models / DB

Cross-cutting: Events/Notifications, Mail, Queue-ready jobs, Scheduled Commands, DB Triggers.

4.2 Request Lifecycle

  1. Browser sends HTTP request to a route defined in routes/web, routes/admin, or routes/api.
  2. Global middleware (CSRF, session, WebP) and route middleware (auth, admin) execute.
  3. Controller invokes a Service for business rules (e.g., FundraiserLevelService, CouponService).
  4. Model layer reads/writes the database; DB triggers maintain derived values.
  5. Response rendered (Blade view) or returned as JSON (API/webhook).

12.User Flow — Fundraiser Level Gating

Business rules that constrain who can raise how much.

FundraiserLevelService::canCreateCampaign() enforces two limits before a campaign can be created:

  • Max concurrent campaigns (max_active_campaigns) — counts active/pending/paused.
  • Max goal amount (max_goal_amount) — hard cap per level.
Level PropertyEffect
max_active_campaignsLimits how many open campaigns a user may have
max_goal_amountCaps the fundraising goal per campaign
status = suspendedBlocks the account from creating campaigns
status = upgrade_pendingFlags a pending level upgrade request
On update, only the goal cap is re-checked (not the count), because the user already owns the campaign. Level is resolved from assignedLevel or a default. This nuance shows careful modeling of real-world fundraiser tiers.

13.User Flow — Store Logic Deep Dive

What happens on CampaignController::store().

  1. Auth check → redirect to login if unauthenticated.
  2. Run fundraiser-level gate; reject with reason if over limit.
  3. Validate all input against CREATE_RULES.
  4. Require ≥1 valid campaign update.
  5. Create Campaign in pending state with unique slug; convert cover to WebP.
  6. Store products (user→pending, admin→approved) and updates.
  7. Clear category cache; send CampaignCreatedMail; redirect to KYC.
Campaign::create([
  'user_id'      => Auth::id(),
  'category_id'  => $request->category_id,
  'title'        => $request->title,
  'slug'         => $this->generateSlug($request->title),
  'goal_amount'  => $request->goal_amount,
  'raised_amount'=> 0,
  'campaign_state' => Campaign::STATE_PENDING,
  'required_level_id' => $check['level']->id,
]);

14.User Flow — KYC Submission

Identity verification from the user's side.

  • KycUploadController: user uploads PAN / Aadhaar / Passport to the private disk.
  • Record scoped per campaign_id + owner — multiple campaigns keep separate KYC records.
  • File stored at kyc-documents/{user}/{campaign}; status set to pending; admins notified.
  • Owner-only access enforced via abort_unless(Auth::id() === ...) on view/serve.
graph TD U[User] -->|GET /kyc/upload| F[KYC Form] F -->|POST file + number| S[Store on private disk] S -->|status=pending| N[Notify Admins] N --> W[Wait for admin approval]

Figure 14.1 — KYC submission and notification.

Sensitive PII (government IDs) is never placed on public storage. The private disk + owner-scoped access + per-campaign isolation means a compromised campaign view cannot leak another user's ID document.

40.Payment — Step 1 Initiate

redirectToPayment()

  • Rate-limited (10 hits / 60s per user/IP).
  • Validates amount within ₹1–₹500,000.
  • Applies coupon server-side (discount never trusted from client).
  • Checks campaign state (rejects expired/paused/rejected).
  • Stores a 15-minute donation session with cart data.

41.Payment — Step 2 Payment Page

paymentPage()

  • Re-validates session (exists, matches campaign, not expired > 900s).
  • Re-validates coupon from DB; falls back to full amount if coupon lapsed.
  • Calculates the 5% platform fee split.

42.Payment — Platform Fee Model

Razorpay charges the donor the full amount. Internally the system splits it: net_amount = amount − (amount × 5%). The campaign receives net_amount; the platform retains platform_fee. Recorded on every donation and aggregated at settlement.
private function calculateFees(float $amount): array {
  $platformFee = round($amount * 5.0 / 100, 2);
  $netAmount   = round($amount - $platformFee, 2);
  return ['platform_fee' => $platformFee, 'net_amount' => $netAmount];
}

46.Payment — DB Trigger for raised_amount

The application does not manually increment raised_amount. A MariaDB trigger recomputes it from the sum of completed donations — the single source of truth. This removes an entire class of bugs (double counting, partial updates, lost writes under load).

CREATE TRIGGER trg_donation_raised_amount_update
AFTER UPDATE ON donations
FOR EACH ROW
  SET c.raised_amount = (SELECT COALESCE(SUM(...),0) ...);
This is a senior-level data-integrity decision: pushing the invariant into the database guarantees correctness even if application code is refactored or a bug slips through.
